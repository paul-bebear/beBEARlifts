# beBEARlifts audit, 26 October 2026

Written 2026-10-26 against `master` at 2fd8e74b, the 122 commits after the October review (`REVIEW-2026-10.md`, written at 07e06e22). Read-only: no code changed.

Each finding has a code. M is money, P is privacy and user harm, D is data loss, X is a crash or dead end, H is code health. "Seen" means the code path was read end to end or a test proved it. "Suspect" means the code points that way but nothing ran it.

Effort is hours for one person who knows the code, with the tests in `test/` run one file at a time.

## Summary for the owner

1. Nothing found lets one user read another user's data. Every database rule on the live Supabase project matches the repo, and the anonymous key can only add an email to the waitlist.
2. One signed-in user can switch off AI for every user until midnight UTC with about 600 web requests. It costs you nothing, but paying beBEAR+ users lose AI that day. See M1.
3. The whole app shares 600 AI calls a day. Around 200 daily free users use all of them, and then paying users are refused too. See M2.
4. Test purchases count as real purchases while `BILLING_ALLOW_SANDBOX` is on. Turning it off breaks Apple's review of every app update. Today any TestFlight tester can get lifetime beBEAR+ without paying. See M3.
5. On the iPhone, food, notes, runs and body scans reach the cloud backup only on days the workout list changes. A lost phone loses every food day since the last workout. See D1.
6. One failed read during an automatic backup can upload empty notes, runs and bear progress over the good cloud copy. See D2.
7. On a shared phone, the second person to sign in gets the first person's workouts, food and private notes uploaded into their account. See P1.
8. Progress photos are still in no backup, and the iPhone keeps all of them in one storage value of up to 200 MB. See D4.
9. Logging a workout has no crash or dead end. Logging food has six. The worst: Back after an AI meal scan throws the estimate away and uses another of the 3 free AI scans. See X1 to X6.
10. Five test files fail under Node 22, and one shows the AI onboarding can never pick the three beBEAR programs. The 38 lint errors are 1 hour of cleanup. See H1 and H2.

## Money

- **M1. One signed-in user can use up the app-wide AI allowance for everyone**
  - Severity: high for paying users, zero cost to you. Seen in the SQL and in the live grants.
  - File and line: `supabase/migrations/20261025000000_store_entitlements.sql:113-117` (the 600-a-day ceiling counts every user's calls together), `:134-136` (a "report" call is allowed whenever its `p_ref` is new, with no per-user limit), `supabase/migrations/20261022034321_ai_caps_and_plans.sql:166-194` (the old zero-argument `ai_usage_take()` still adds to the same ceiling and is still granted to every signed-in user; the API stopped calling it), `api/ai/report.mjs:40-43` (`workoutId` comes from the request body).
  - Scenario: a signed-in user posts `{}` to `/rest/v1/rpc/ai_usage_take` 600 times with the public key and their own token, or posts 600 reports with a new `workoutId` each. Both count toward the ceiling, and the first costs no AI tokens. Every AI route then answers 429 "The app's daily AI allowance is used up" to every user, beBEAR+ included, until 00:00 UTC. Sign-up is open, because Apple and Google sign-in create accounts.
  - Fix: a migration that revokes `execute` on `public.ai_usage_take()` from `authenticated` (or drops it), and caps the "report" kind per user per day, for example 10. Make the ceiling check refuse one user once they hold more than a tenth of the day's total.
  - Effort: 1.5 hours with a case in `supabase/tests`.
- **M2. The 600-a-day ceiling is fixed in SQL and shared by free and paying users**
  - Severity: medium now, high once more than about 150 people use AI daily. Seen.
  - File and line: `supabase/migrations/20261025000000_store_entitlements.sql:114-117`, `api/_auth.mjs:100-105` (the refusal text).
  - Scenario: 200 free users each use their 3 daily AI calls by mid-afternoon UTC. A user who paid for "30 AI uses a day" is refused at their first call with a message that blames the app. Nothing tells you the ceiling was reached. The live peak so far is 6 calls in one day, so this is a growth problem.
  - Fix: move the ceiling into a one-row config table you can change from the dashboard. Keep a separate share for plus users, or skip the ceiling for them because their own 30 and 150 caps already bound them. Log a line or send an email at 80 percent.
  - Effort: 2 hours.
- **M3. Test purchases unlock beBEAR+, and turning that off breaks App Review**
  - Severity: medium. Seen in the code and in the Vercel environment list. The value of the variable was not read.
  - File and line: `api/_billing.mjs:87-88` (a sandbox purchase counts only when `allowSandbox`), `:111` (`BILLING_ALLOW_SANDBOX === "1"`), `docs/bebear-plus.md:17` ("set `BILLING_ALLOW_SANDBOX=1` until the app goes on sale"). `vercel env ls` shows `BILLING_ALLOW_SANDBOX` set for Production.
  - Scenario, flag on: TestFlight purchases are free sandbox purchases. A tester buys `bebear_plus_lifetime` at no charge and the server stores a lifetime grant with no end date. Flag off: Apple reviews every update with sandbox purchases. The reviewer buys, the app says "Purchase done. beBEAR+ turns on in a moment" and never turns it on. That is a common rejection reason under guideline 2.1.
  - Fix: keep sandbox purchases allowed, but give a sandbox grant an end date (for example 7 days after `snapshotAt`) in `Billing_entitlementRow`, so no sandbox grant is ever lifetime. Or allow sandbox only for an allow list of reviewer and tester user ids in an env variable.
  - Effort: 1.5 hours with cases in `test/billing.test.ts`.
- **M4. `redeem_pro_code` has no attempt limit**
  - Severity: low. Seen. The live `pro_codes` table is empty.
  - File and line: `supabase/migrations/20261022034321_ai_caps_and_plans.sql:58-86`.
  - Scenario: if you create short codes such as `BEAR2026`, a script can guess them, because each wrong guess costs one request.
  - Fix: make codes 16 random characters. Or count failed attempts per user per day in a table, the way `find_profile` does.
  - Effort: 0.25 hours for the rule, 1 hour for the counter.

Checked with no finding:

- The RevenueCat webhook compares the full `Authorization` header with `REVENUECAT_WEBHOOK_AUTH` in constant time. Without the variable it refuses everything (`api/_billing.mjs:16-23`).
- The server never trusts the phone about a purchase. `/api/billing/sync` asks RevenueCat by the signed-in user id (`api/billing/sync.mjs:21-35`).
- `store_entitlement_put` and `account_plan_effective` are callable only by the service role, live and in the repo.
- A refund or an expiry turns beBEAR+ off: `account_plan_effective` needs `expires_at > now()`, and a missed webhook is repaired by the sync at the next app start.
- The phone signs in to RevenueCat with the Supabase user id before the paywall opens (`src/models/purchasesIdentity.ts`, `src/utils/purchases.native.ts:61-86`), so a purchase cannot land on an anonymous id.
- AI caps live on the server. The plus features that run on the phone (Week Insights, muscle views, trend lines) read a stored plan, so a web user who edits IndexedDB gets them. They make no server or AI call.
- No secret key is in the repo. The RevenueCat `appl_` key and the Supabase publishable key are meant to ship.

## Data loss

The October data findings were checked again. D1, D2 (for writes), D3, D5 to D12 are fixed on master. D4, progress photos in no backup, is still open. The iPhone runs the same `JsonStore` on MMKV (`src/utils/indexeddb.native.ts`), and MMKV throws on a failed write, so writes are as safe as on the web.

- **D1. On the iPhone, food, notes, runs and scans reach the cloud only when the workout list changes**
  - Severity: high. Seen in the code.
  - File and line: `src/models/cloudBackup.ts:126-136` (`CloudBackup_isAutoDue` looks at `history` only), `src/components/app.tsx:143-155` (the launch and return catch-up runs only in the web app), `src/App.native.tsx:497-510` (the iPhone's "active" handler never calls `Thunk_cloudCatchUp`), `src/components/cloudBackupAfterWorkout.tsx:7` (the only other automatic upload).
  - Scenario: a user trains on Monday and logs every meal and a journal note each day. On Saturday the phone is lost. The cloud copy is Monday's, so five days of food and notes are gone. If iOS suspended the app during Monday's upload, nothing retried it either.
  - Fix: dispatch `Thunk_cloudCatchUp()` at launch and in the "active" branch in `src/App.native.tsx`. Make `CloudBackup_isAutoDue` also compare a mark of the other stores: entry counts plus the newest timestamp of food, notes, runs, scans and check-ins.
  - Effort: 2.5 hours with tests in `test/cloudBackup.test.ts`.
- **D2. A failed read during an automatic backup uploads empty stores over the good copy**
  - Severity: high. Seen in the code, and proven by a scratch test: a notes read that throws gives a backup with `"notes":[]` and no error.
  - File and line: `src/utils/jsonStore.ts:55-68` (`load()` catches the error and resolves with `current`, still `empty()`), `src/utils/fullBackupFile.ts:17-33` (`FullBackupFile_build` reads every store with `load()`).
  - Scenario: Safari's IndexedDB fails for a moment while the finish screen backs up. Notes, runs, body scans and the bear store go up empty in `latest.json`. A restore on a new phone writes them empty, and spent honey resets to 0. Food is safe only because an empty food log makes the compare step ask first.
  - Fix: add `loadStrict()` to `JsonStore_create` that rejects when the read fails, and use it in `FullBackupFile_build` so the backup stops with an error.
  - Effort: 1 hour.
- **D3. A second device replaces notes, runs and edits that only the cloud has**
  - Severity: medium. Proven by a scratch test.
  - File and line: `src/models/cloudBackupCompare.ts:44-57` (`CloudBackupCompare_decide` compares workout ids and food entry ids only).
  - Scenario: you log a run and two notes on the iPhone, which uploads them. Later the web test bed, last synced a week ago, finishes a workout. The cloud has no workout or food the web lacks, so its upload replaces `latest.json`. The run and the notes survive only in one weekday copy for up to 6 days. An edited workout (same id) is lost the same way.
  - Fix: when the cloud's `exportedAt` is not the one this device last uploaded, ask before replacing, whatever it holds.
  - Effort: 1 hour.
- **D4. Progress photos are in no backup, and the iPhone stores them all in one value**
  - Severity: medium. Seen for the backup. Suspect for the memory risk: not run on a device.
  - File and line: `src/utils/fullBackupFile.ts:17-33` (no photo store), `src/models/progressPhotos.ts:13-15` (200 photos of up to 1 MB as data URLs), `src/utils/progressPhotoStore.ts`.
  - Scenario: each added photo reads, parses and rewrites the whole value, up to 200 MB, in the same MMKV instance as the workouts. iOS can end the app for memory during that write. A new phone gets no photos back.
  - Fix: save each photo as a JPEG file in the documents folder and keep only an index in MMKV. Upload each file to `<uid>/photos/<id>.jpg`.
  - Effort: 4 hours.
- **D5. A store that cannot be parsed stays locked**
  - Severity: low. Seen.
  - File and line: `src/utils/jsonStore.ts:39-53` and `:70-82`.
  - Scenario: the food log's JSON is cut short. The raw text is copied to `bebear_foodlog_unreadable`, which is good. After that every `update` alerts "Could not read saved data", the diary shows empty, and no food can be logged again on that phone.
  - Fix: after the copy, offer "Restore from cloud" or "Start this log again" in the alert.
  - Effort: 1 hour.
- **D6. One bad field resets the whole bear store**
  - Severity: low. Proven by a scratch test.
  - File and line: `src/models/bearStoreData.ts:18-32`.
  - Scenario: if `celebratedLevel` is not a whole number of at least 1, the parse returns the empty store. Spent honey goes to 0, the chosen bear is lost, and every level-up and badge celebrates again.
  - Fix: parse each field with its own fallback.
  - Effort: 0.5 hours.
- **D7. Old records are dropped without a word**
  - Severity: low. Seen.
  - File and line: `src/models/musicLog.ts:15` (60 music sessions), the warmup store (60 plans), the report store (200), the clip store (300).
  - Scenario: at 3 workouts a week, the music for each set is gone after about 5 months, and the backup holds only the trimmed copy.
  - Fix: raise the caps, or say in the screen that the oldest records are removed.
  - Effort: 0.5 hours.

## Crashes and dead ends on the two core flows

No crash or dead end was found in the fork's workout code. The finish screen's fork models handle bodyweight-only, short and empty workouts. The food parsers, the Open Food Facts and USDA parsers and `FoodPhotoEstimate_parse` do not throw on bad input. Every finding below is on the food flow.

- **X1. Back from "Serving size" after an AI scan throws the estimate away, and on the iPhone reopens the camera**
  - Severity: high. Proven by a scratch test for the step, seen in the code for the camera.
  - File and line: `src/models/foodScanSteps.ts:125-128` (`backFrom` turns `serving` into `{ kind: "camera", mode }` and keeps no items), `src/components/foodPhotoPanel.native.tsx:19-22` (the mount effect starts `NativeFoodCapture_meal("camera")`).

  - Fix: keep the last choices in the camera step, pass them to `FoodPhotoPanel` and `FoodDescribePanel` as the first state, and skip the camera launch when choices exist.
  - Effort: 2 hours.
- **X2. A failed food save leaves Add and Log dead until the screen is closed**
  - Severity: medium. Proven by a scratch test of the guard flag.
  - File and line: `src/components/screenFoodAdd.tsx:178-186` (`logBasket`) and `:188-200` (`logServing`) set `isLoggingRef.current = true` and await `FoodLogStore_update` with no `try`/`finally`.
  - Scenario: the write fails, for example when progress photos have filled Safari's storage. The alert says "Could not save data… Try again." Every later tap on Add or Log does nothing, and the food is not saved.
  - Fix: reset the flag in `finally` and call `goBack` only after a save that worked. Do the same in `saveGroup`.
  - Effort: 0.5 hours.
- **X3. A late barcode answer opens the wrong product**
  - Severity: medium. Proven by a scratch test for the late answer. Suspect for how long the spinner can hang.
  - File and line: `src/components/screenFoodAdd.tsx:155-163` (`onBarcode` sends the result whatever the screen shows now), `src/models/foodScanSteps.ts:163-164` (`barcodeFound` is taken from any step), `src/utils/foodApi.ts:24-29` (no time limit on the request).

  - Fix: carry the code in `barcodeFound` and `barcodeMissed`, and ignore them unless the step is `reading` for that code. Add a 15 s `AbortController` to `request()`.

- **X4. "Same as yesterday" copies into today, not the day the Journal shows**

  - File and line: `src/components/foodRepeatList.tsx:22` (`FoodLog_dayKey(new Date())`), `src/models/foodRepeat.ts:78`.
  - Scenario: the user goes back to 20 October in the Journal to fill a missed day, taps add, then "Same as yesterday". The list shows the day before the real today, the copies land on the real today, and 20 October stays empty.

  - File and line: `src/components/foodPhotoPanel.native.tsx` and `src/components/foodLabelPanel.native.tsx` have no session check (the web panels show `FoodAiSignIn`), `src/utils/aiRequest.ts:8` ("Open Progress → the gear icon → Cloud backup"; the tabs are now Home, Journal and My bear).
  - Scenario: a signed-out user photographs a meal, waits, and reads a sign-in message with no button that names a path which does not exist.
